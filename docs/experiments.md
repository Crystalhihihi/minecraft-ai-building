## E0:便宜工人能否按任务书施工 —— ✅ 通过(2026-07-30)

- **结论**:K2.7 Coding(managed 套餐)工人能力合格:读任务书/选风格卡/propose/勘察/放置零错误/渲染自检/诚实汇报。塔(7x7x21,地基+墙+扶壁+窗+垛口+人字顶)结构核对全对
- **附带发现 1**:选址审美是 planner 的活——工人把塔盖在了山腰里(埋进深板岩),施工全对但位置失败。planner-worker 分工被反例证实

- **附带发现 3**:bridge 参数类型脆弱性(Postel 宽容化已修,85/85 测试绿)
- **附带发现 4**:基础设施税是最大隐性成本——dev server 超时杀 job、选址确认存内存随重启归零(加固项:SiteGate 状态落盘、job 恢复、429 自动续跑)

## E1:并发放置吞吐 —— ✅ 放置不是瓶颈(2026-07-30)

- 4 并发 14x30x14(5880 each):全部 0.3s 完成,零失败,聚合 ~79k blocks/s
- 2 并发 30x35x30(31500 each):0.2-0.4s,零失败,聚合 ~161k blocks/s
- 早期"32³≈1.5s"的成本大头是**首次 chunk 加载**(ticket 系统一次性),不是放置本身
- **结论**:热区块并发放置 ~10⁵ blocks/s,比 agent 思考速率(分钟级)高 4-5 个数量级。并行建造永远不会卡在放置上,瓶颈只有模型延迟

## E4:并行 A/B —— ❌ 首轮输了(2026-07-31,K3 planner + 4×K2.7 worker)

- **数据**:K3 planner 拆 4 区(互不相交,接缝责任写死),4 个 K2.7 worker 并行盖同规格中世纪庄园
  - 墙钟 **28.3 分钟**(最慢 zone1 决定)vs E2 基线 16.1 分钟 → **慢 1.76 倍**
  - 总劳动量 218 轮 / 405 调用 / 40,757 块 vs E2 的 36 轮 / 52 调用
  - 分区:#13(西北,含主楼西半)28.3min/82r/126c/9771b;#14(东北)13.3min/42r/75c/15666b;#15(西南,门楼+主路)12.2min/44r/84c/7678b;#16(东南)12.9min/48r/120c/7642b
  - 零失败、零 429、零自愈(managed 通道 4 并发稳定)
- **质量**:全景 topdown 渲染——幕墙闭环、四角塔、门洞+主路、主楼屋顶全在,结构完整(渲染:`scratch/phase7/e4/verify/manor_topdown.png`)
- **败因分析**:
  1. **K2.7 轮次肥胖**:K3 单干整个庄园 36 轮;K2.7 干一个区就要 42~82 轮。每轮 latency 相近,轮次多=墙钟长。4 并发并没有把"总轮次"除掉,反而每人都要走完整流程(读文档/勘察/自检)
  2. **planner 均衡失误**:zone1(主楼西半+塔+两墙)是最慢路径 28.3min,是其他区的 2.1 倍——按方块数估均衡没用,主楼复杂度(屋顶/骨架/箭窗)才是时间大户
  3. **基础设施税每人一份**:每 worker 渲染自检 ~10 次 + 勘察 + 读 AGENTS.md,4 人就是 4 份固定开销
- **配套改动**:`/aibuild @path` 从 aibuild 根目录读任务书(commit d496881+,绕开 RCON 长度上限;修 getWorldPath 未 normalize 导致 startsWith 误判);config 新增 `agent_model`(-m 注入 spawn)
- **待定方向**:a) 全 K3 并行(轮次少,可能直接赢);b) planner 按复杂度而非方块数配平(主楼独占一区);c) 减少自检频次;d) 2 worker 而非 4(固定开销减半)
